# What a researcher can do with the Agenetic graph

November 20, 2026 · Product and engineering review for Agenetic by Groundplanes

A researcher corrects an interview transcript. Which conclusions used the old wording? Where exactly did the reviewer read it? Can another review replace that decision, and can the researcher reopen the same question tomorrow? Those questions exposed a larger gap than the shape of the graph. The first Atlas pass could show the source, the agent and the task. Answering a question that crossed those records still required opening them individually and remembering the path.

The new **Investigate** control sits alongside Atlas, Flow and Freeform. It reads the open workspace and works offline. The passages, route labels and region membership below come from actual records. No model or additional service participates in these operations.

## Try it in a workspace

| Question | Where to go | What to look for |
| --- | --- | --- |
| How does this note reach that task? | In Fieldwork, open **Graph → Investigate → Paths**. Select **Project brief** and **Compare interview findings**. | The route through **Research** says the note is used by the agent and the agent is assigned the task. Reverse the endpoints and try **Either direction** to see the inverse relationship wording. **Declared sources only** follows an actual incoming reference listed by the receiving research record. Drafts can declare sources. |
| Why are these records in the same patch of the Atlas? | Open **Regions**, choose a named hub, then rotate the graph. | The outline follows the projection of the member records. The list gives exact membership and separates internal links from links that cross the boundary. An unrelated point can project inside a region's outline. Highlighting and the member list identify membership. |
| Where did this claim come from? | Open a reviewed claim, choose **Inspect evidence**, then **Inspect passage**. | The reviewed version and current source are shown together. The source snapshot and decision carry their own dates where recorded. An exact match is highlighted. Multiple indistinguishable occurrences, a missing passage, a removed source link and a missing source receive explicit treatment. **Read current source** opens the existing reader. |
| What does correcting this source affect? | Open the source and choose **Check source impact**. Select a claim, then **Review claim again** if its original draft is available. | Direct and transitive citation dependencies appear with their distance and current eligibility. The original statement and source are preselected for another review. The decision starts blank. Saving a new decision on the same statement supersedes the earlier review while retaining its text and snapshot. |
| How do I resume this after another edit? | Choose **Save investigation**, name it, then reopen it from **Saved investigations**. | The workspace retains a query using record IDs. Names can change. Removing or hiding an endpoint produces an unavailable result. Running a saved investigation never restores removed material. |

## Implementation choices and their consequences

**Route search.** Build a workspace-local adjacency index from the same typed relationships as the rendered graph. Breadth-first traversal records equal-length predecessors and reconstructs at most four results to detect overflow. The UI displays three. Stable tie-breaking makes the displayed choices reproducible when the input order changes. Either-direction traversal preserves the stored direction on each hop. Isolated records, cycles, self-loops, duplicate links and missing endpoints have explicit tests. A filtered explorer returns to its previous query when the investigation closes. Large endpoint pickers allow a name search across the whole workspace and keep a bounded list of choices in the DOM.

**Evidence.** A selected quotation records up to 40 UTF-16 code units on either side, alongside Agenetic's existing source revision. When the quotation repeats, a unique context match resolves the location. A manually pasted or older quotation without context can still locate a unique occurrence. Ambiguous occurrences remain unresolved. Text comparison uses the extracted source text and original characters. OCR changes, whitespace normalization and page coordinates need their own locator. The existing eligibility check conservatively invalidates a reviewed source after any change to its captured text, including a change outside the quotation. Eligibility describes reuse in Agenetic. The researcher judges whether a conclusion is warranted.

**Impact.** A reverse index follows recorded quotations, including citations whose graph edge was subsequently disconnected. Traversal can pass through a superseded intermediary to find a current dependent. Repeated paths and cycles count a dependent once at its shortest citation distance. The UI sorts claims that need a source check first. A missing live edge is never redrawn as an existing graph edge. Brief citations already have a separate stale-citation warning in the Research desk. This impact list currently covers evidence records and supported claims.

**Regions.** Atlas computes a deterministic multi-source traversal from agent and high-degree hubs. Remaining connected components get a region, and isolated records share a separate group. Direction is ignored for grouping. Internal and boundary counts use actual workspace links. The selected region's outline is a convex hull of projected coordinates. Hub membership can move after editing topology. This is a navigational grouping and has no effect on source eligibility.

**Persistence and performance.** Saved records contain a name, workspace-local query inputs and a stable ID. Each reopen computes a fresh result. Opening a query writes no links. Region drawing and label placement reuse graph coordinates. During a drag only the decorative contours are sampled more sparsely. Actual records and their links update at each processed rotation, and full contour detail returns on release. Overview labels give the active records priority and skip measuring labels that are already hidden.

## Measurements from the actual renderer

Headless Chromium on Linux, 1440 × 1000, synthetic workspace. Record i links forward to i+1 and i+17 where those exist. Path search runs from the first record to the last. Times are milliseconds. Each row uses 30 warm search samples or 12 warm rotation samples. The 10,000-record case exercises the query engine only. The 600- and 1,200-record cases create real SVG nodes and edges in the shipping renderer.

| --- | ---: | ---: | ---: |
| 600 / 1,182 | 0.6 / 2.7 | 22.0 / 14.4 | 73.5 / 48.8 |
| 1,200 / 2,382 | 1.0 / 3.4 | 30.1 / 14.8 | 153.8 / 66.1 |
| 10,000 / 19,982 | 8.7 / 41.6 | — | — |

The baseline used full contours during a drag and the old label pass. The revised pass uses sampled contours mid-gesture. Rotation times measure the synchronous update. A following geometry read in the label pass can force browser layout. The actual drag handler defers label placement until release. At 1,200 records a full-detail release plus a label pass measured 70.2 ms in a single observation. Neither these timings nor the 13,211 SVG descendants in that case establish a Windows frame rate. Results will vary with density, text length, distribution, hardware and run order.

Reproduce with Playwright and a compatible Chromium executable. Ordinary audit runs omit the benchmark. The opt-in run writes the raw measurements to `audit-results/investigation-benchmark.json`.

```sh
node --test tests/*.test.mjs desktop/tests/*.test.cjs
AGENETIC_GRAPH_BENCHMARK=1 CHROMIUM_EXECUTABLE_PATH=/path/to/chromium node tests/browser-audit.mjs
node desktop/scripts/prepare.mjs
```

The final run passed 111 unit and desktop tests and 39 Chromium workflow checks. The browser exercised a repeated quote, an edited source, a replacement claim decision, hidden sources, missing endpoints after reload, a failed save and retry, workspace isolation, large-list endpoint selection, mobile framing and Atlas rotation. Desktop preparation produced a renderer containing the same investigation script and styles. Packaged Windows interaction and a moderated researcher study remain unverified.

## What to implement next and how to decide

| Priority | Concrete change | Design or data dependency | Proposed acceptance gate |
| --- | --- | --- | --- |
| 1. Make dates usable across views | Add a timeline beside the graph. Brush a period and inspect the matching records, reviews and source revisions. Save the date-range query. | Store occurrence date, import time and review time as separate fields. Preserve offsets and precision, distinguish an inferred date, and give undated legacy imports an explicit group. The first version can show existing timestamped review events. | A reimport never makes an old interview appear to have happened today. A date-only source remains on the same calendar day across timezones. The timeline, list and graph return the same record IDs for a saved period. |
| 2. Scale the Atlas on Windows | Add a zoom tier showing one selectable mark per region and counts. Expand one region in place. Keep path endpoints and keyboard targets available across tiers. Profile the packaged renderer before changing technologies. | Separate the full graph model from the visible projection. Use deterministic anchors and an accessible member list. Test a chain, a dense hub, many disconnected records and long labels. Consider a canvas edge layer with an HTML/SVG selection overlay if profiling identifies DOM costs. | Record pointer-to-paint p50/p95, label-settle time, peak memory and dropped frames on an integrated-GPU Windows laptop at 1k, 5k and 10k records. Proposed targets are under 33 ms p95 during input and under 100 ms after release at 1k. |
| 3. Let researchers ask for a view in their own words | Map requests such as “what else depends on this interview?” onto the same impact query. Show the resolved record and operation. Let the user choose when names collide. | Define a small validated local query schema using the shipped path, impact and region operations. Compile the first few common requests deterministically. Evaluate a local model against that baseline for paraphrases. | Use 50 labeled requests, including ambiguous names and unsupported temporal requests. Measure scope, endpoint accuracy and truthful no-result handling. A read request cannot mutate a source or start a model run without the user's chosen workflow. |
| 4. Suggest related passages and compare competing evidence | Retrieve candidate passages locally. Show both excerpts, where each came from and why it was suggested. Record acceptance, rejection or unresolved status. Add a claim-by-source matrix when many claims share sources. | Use the existing exact quotations and revision IDs as the acceptance boundary. Start with lexical retrieval, then compare a local embedding index on paraphrases. Keep model/version information with the suggestion. | Hand-label related and unrelated passages, including similar wording from different interviews. Report precision among the top five and first useful result time. Rejected suggestions stay dismissed. Accepted relationships retain their review trail after reimport. |

These priorities serve different users. The timeline unlocks a question the current product cannot reliably answer. The denser Atlas directly addresses the observed rendering cost. For a release aimed at multi-thousand-record vaults, run the Windows measurement gate first and use it to order those two investments.

## Validation still needed with researchers

Recruit six people who work from interviews, papers or case notes. Counterbalance the old and new builds and use matched workspaces with the same graph structure and different record names. Ask each participant to explain a path, identify the exact second occurrence of a quote, find the claims affected by an edit, and repeat the investigation after an interruption. Include one case with a removed source and one visually adjacent unlinked record. Record time to correct answer, wrong-source selections and whether anyone describes adjacency or assignment as evidence. Test keyboard-only navigation as a separate condition.

A proposed pilot gate is five of six participants completing each task without help, zero false evidence attributions, and a lower median time to reopen the correct source than the old build. Six participants would guide a design iteration. Broader performance or usability claims would need more data.
